# 源码兼容变化审查门禁与迁移保护范围

P0 的目标是建立后续改造所需的保护与恢复基础。每个子项以完整工程事项交付，必须同时包含实现、相关接入、测试、使用说明及验收证据。不能以某个工具可运行代替整个阶段验收。

内部迁移的每个增量都必须保留既有外部框架接入、全部算子和实现能力、默认选择及功能/性能。允许新旧接口并存，新入口显式启用，旧入口和执行路径保持可用；目录迁移不能要求外部框架修改调用或配置。本工具增加源码审查保护，不参与运行、生成、安装或后端选择，不能代替真实运行等价验证。

## 分项及完成条件

| 子项 | 完整交付边界 | 完成条件 |
| --- | --- | --- |
| P0.1 源码变化审查 | 采集器、初始快照、差异检测、正反例测试、CI、基线更新流程 | 对真实仓库检查通过；声明/策略变更及增删文件能被拒绝；CI 配置已接入 |
| P0.2 真实构建与调用验证 | 配套 RT/工具链锁定、安装消费者、默认索引与导出检查、严格测试通道 | 对选定构建配方完成真实编译安装和调用；必需测试缺失/跳过即失败 |
| P0.3 生产发布与恢复 | 必需业务/平台清单、性能预算、旧制品、负责人、恢复步骤与演练 | 每个生产配方具备实际业务结果及符合恢复时限的演练证据 |

P0.1 已经完成独立审核及远端门禁验证。P0.2 首个 Linux CPU Add/Gemm 配方正在开发，完整边界见 [安装消费者验证](../../verification/cpu/README.md)，实际通过状态以对应提交的工作流为准。P0.3 尚未启动；不提供带空值的生产清单，也不改变现有硬件 CI 配方。P0 整体仍须满足架构基线的所有要求。

## P0.1 的保护范围

[compatibility-baseline.json](compatibility-baseline.json) 记录 683 个不同输入文件的规范化文本 SHA256（P0.1 审核交付时 676 个，本次 CPU 验证通道新增 7 个输入），分为三组：公共声明输入、调度/生成/算子选择策略、构建/依赖配方。公共声明输入包括安装所需的根级核心头和公共辅助头；配方包括嵌套 CMake、`.cmake.in` 安装模板、厂商 compiler wrapper、custom 构建入口、linked 依赖 YAML、源码准备工具、已有硬件 CI 入口及新增验证配方。根 `ops.json` 存在时也纳入保护，其新增同样触发审查；不改变现有自动读取行为。一个文件可以属于多个审查组，但文件总数去重。采集范围在 [采集器](../../scripts/compatibility_baseline.py) 的 `GROUPS` 中显式定义。

首轮独立审核发现上述选择配置和若干现用构建输入未被原始范围覆盖，本次扩展增加 67 个既有输入文件，并补充每类文件独立的新增/修改/删除负例；没有改变原有输入内容。外部 CI 仓库维护的镜像定义不在本源码快照内，镜像 digest、工具链与依赖配套由真实构建验证阶段锁定，不将本仓库没有的 `images/` 内容宣称为已保护。

这是保守的源码变化审查器。公共头增加注释或内部实现变化也可能触发审查；它不能推导变更是否破坏 ABI。默认实现的选择逻辑由源码指纹保护；逐算子/设备的实际默认映射、生成后 Python 导出和安装二进制符号在 P0.2 验证。现有 `src/base` 输入不能直接宣称为正式稳定契约。

源码中未落盘的生成文件不纳入本次快照；当前源码之外的运行时、设备状态和业务数据也不属于 P0.1。固定源码基线不等于锁定了 CI 中浮动的 InfiniRT。

本项是迁移前的保守门禁。新增公共算子暂时会要求审查并更新快照；P3 建立契约版本校验后，应以契约兼容检查接替对应保护，不把手改中央快照作为最终普通算子接入流程的一部分。

## 本地与 CI 使用

在仓库根目录执行，Python 3.12，仅使用标准库，无需 Torch、InfiniRT、CMake 或加速器：

```text
python -m unittest discover -s tests -p test_p0_guards.py -v
python scripts/compatibility_baseline.py check --baseline docs/refactor/compatibility-baseline.json
```

[Compatibility Baseline 工作流](../../.github/workflows/compatibility-baseline.yml) 在 push、PR 和手动运行时执行相同命令；不使用路径过滤，避免新增声明未触发检查。

- 退出 0：受保护源码未变化，或新快照成功采集。
- 退出 1：发现新增、删除或内容变化，需要显式审查。
- 退出 2：基线/源码缺失、采集范围不匹配、重复 JSON 键、非法版本/路径/hash 或格式错误，不能当成通过。

同一内容的 LF/CRLF 差异不触发误报。检查命令不写源码、不重建基线，不需要网络。

GitHub 上的首次实际执行和将该 job 设为分支保护必需检查，需要代码进入远端后完成；本地验收不声称已经执行了 GitHub runner。

## 合法变更如何更新基线

检查失败应先阅读按组输出的 `added/removed/changed`，确认签名、默认值、旧索引、依赖、安装行为的影响。源码指纹变化本身不是禁止修改；评审必须说明兼容性及补充验证。

用新路径采集候选，不能覆盖原基线：

```text
python scripts/compatibility_baseline.py capture --baseline candidate-baseline.json --source-revision FULL_40_CHARACTER_SOURCE_COMMIT
```

`--source-revision` 由实施者提供，指向分析所依赖的源码提交；内容指纹同时反映工作树变化，采集器不把该参数当成“工作树干净”的证明。

候选 diff、受保护变更、对应测试与兼容说明放在同一评审中。确认后显式替换正式 JSON，删除临时候选，重新运行本地/CI 检查。CI 没有自动更新或自动批准基线的步骤。修改 `GROUPS` 时必须说明保护范围增减，不能通过缩小范围消除失败。

初始快照依据提交 `3ac67190a5996dbf9fe03dc8d8eb68847715ce34`。后续有意更新允许替换当前正式基线，历史通过 Git 保留；与不可覆盖的历史验收报告是不同类型的文件。

## 回退与验收

本项仅新增文件；移除该工作流、采集器、快照及专用测试即可撤回，不影响算子调用路径。不得通过禁用整个硬件 CI 来绕过检查。

验收覆盖：真实仓库一致；声明内容/默认配置/构建配方变化；文件新增/删除；缺失源码/空基线；格式、版本、路径及 hash 校验；重复 JSON 键；CRLF/LF；拒绝覆盖已存在基线；命令行成功/变更/错误退出码。CI 运行结果见对应提交的 Compatibility Baseline 工作流日志；本地验证记录独立归档，不作为源码依赖或生产安装内容。
